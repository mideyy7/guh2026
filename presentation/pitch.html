Criterion 2 · independent decision-making

No dispatcher. Every actor decides for itself.

  • Each actor is its own n8n instance with its own private store.
  • It senses, scores tasks and bids on its own.
  • Peers agree using CBBA (Consensus-Based Bundle Algorithm): each actor builds a “bundle” of rescues it bids for, then peers reach consensus with no auctioneer. Higher bid wins, actor ID breaks ties, fresher information wins conflicts.

How CBBA works · Consensus-Based Bundle Algorithm · Choi, Brunet & How, MIT
1 · Bundleeach actor, on its own

Each rescue team scores every rescue it knows about: how urgent the people are, how soon it could reach them, and how much work it already has. It picks its best few rescues (its “bundle”) and records a bid for each.

2 · Consensuswith every peer it can reach

Actors swap bid tables and apply the same rules: the higher bid wins, a lower actor ID breaks a tie, and fresher information beats older. Because every actor applies identical rules, they all reach the same answer without an auctioneer.

3 · Release & rebiduntil nothing changes

An actor that is outbid drops that rescue and every rescue it planned after it, because those plans assumed the lost one. It then rebids. Within a few rounds every actor agrees who rescues whom.

Example: Drone 02 spots Amara’s family. Rescue 01 is 3 streets away and bids high; Rescue 02 is across the river and bids lower. Both see each other’s bids, both conclude Rescue 01 wins, and Rescue 02 moves on to the next rescue. Nobody told them. During a blackout each island runs CBBA among the actors it can reach; when links return, the islands run it again and settle on one plan.

Say: “This isn’t a shared database. Each column is one actor’s own belief, read from its own store.”

CBBA in one line: “Each team bids for a bundle of rescues, and they agree among themselves who gets what, with the same rules everywhere and no auctioneer.”

If pushed: CBBA is a published algorithm (Choi, Brunet & How, MIT, 2009). We tested that it always reaches one conflict-free plan, including after a network split, over hundreds of random cases.

Criterion 3 · resilience when communications fail

Cut the network. The islands keep rescuing.

  • A chaos proxy sits between every actor. Cuts are real refused connections, not a label.
  • Blackout splits the swarm into three islands and cuts HQ. Each island keeps a drone and a team.
  • A new distress text only reaches the island whose drone is in range. Memories diverge, as they would in reality.

The swarm heals itself.

n8n track · a real task, automated, running on its own

n8n is the dispatcher, seven times over.

hive-tickwebhook · every tick

Read sensors, spot survivors, bid for rescues, move, rescue.

hive-gossipschedule · every 4 s

Share discoveries with every team it can still reach.

hive-mergewebhook · peer message

Merge what others found; settle who owns each rescue.

hive-interpretwebhook · distress text

Claude turns a messy text into a structured rescue task.

The real task is rescue coordination, a human dispatcher’s job. Nobody presses run: every workflow fires itself on a schedule, a peer message or an incoming text, and keeps running when the network is cut.

Built on n8n · not a script with n8n on the side

Every decision in HIVE runs inside an n8n workflow.

7independent n8n instances, one per drone or rescue team
28live, published workflows across the swarm (4 per actor)
196n8n nodes doing the work: 28 in every actor
0central servers. No workflow ever calls another actor’s n8n directly
  • Triggers start everything. A Schedule Trigger runs gossip every 4 seconds; Webhook triggers fire on each tick, each peer message and each distress text. Nobody presses run.
  • Code nodes are the brain. The CBBA (Consensus-Based Bundle Algorithm) allocation, version-vector merging and search logic run in n8n Code nodes, the same code we unit-tested and benchmarked over 270 runs.
  • HTTP Request nodes are the senses and the radio. They read the actor’s sensors, call Claude to read distress texts, save to the actor’s own store, and send gossip through the network.
  • One execution at a time per actor. We set n8n’s concurrency limit to 1, so each instance behaves like a true actor: it handles one message at a time and never corrupts its own memory.

Why n8n fits this problem

  1. Visible decisions. Judges, operators or a rescue coordinator can open any actor and see exactly how it decides.
  2. Independent by design. Each instance has its own triggers, memory and failures. Cut its network and it keeps running.
  3. Easy to extend. Adding a supply drone or an SMS gateway is a new workflow, not a rewrite.
  4. Identical everywhere. All seven actors run byte-identical workflows; the role comes from each actor’s own store.
